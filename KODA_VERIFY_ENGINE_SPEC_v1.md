## 0. THE BRUTAL TRUTH THIS PRODUCT IS BUILT ON

Every African merchant already has a payment API installed. It arrived pre-loaded on their SIM card.

When a customer pays via M-Pesa, Orange Money, Airtel Money, Africell Money, MTN MoMo, or Wave, **two artifacts are generated within seconds, without anyone signing anything:**

1. The **customer** receives a confirmation with a transaction reference (e.g. `TXN ID: CI240717.1432.A88213`).
2. The **merchant** receives a confirmation SMS on their registered SIM containing: reference, amount, sender name, sender number (partial), timestamp, new balance.

That merchant SMS is a **cryptographically-anchored fact issued by the telco itself**. It cannot be generated by the customer. It is the ground truth of the payment.

Every existing "integration" product ignores this and tries to negotiate B2B API access with the telco: 6–18 months of contracts, paybill registration, revenue-share extraction, per-country repetition, and frequent flat rejection for SMEs. That is why 90%+ of African online commerce still ends with *"send me a screenshot of the payment."*

**KODA does not integrate with the telco. KODA reads what the telco already sends the merchant, structures it, and turns it into a webhook.** The verification loop closes on the merchant's side of the transaction — the only side that can't be forged by a fraudulent buyer.

This is not a theoretical mechanism. SMS-ledger reconciliation is how thousands of Kenyan, Congolese, and Ivorian merchants already verify payments manually every day. KODA is that manual behaviour, industrialised, agent-supervised, and exposed as a 3-endpoint API.

## 2. THE CANONICAL FLOW (8 STEPS, ~40 SECONDS END-TO-END)

**Actors:** Customer (any phone) · Merchant (Android phone running KODA Sentinel app) · KODA Cloud · Merchant's system (WhatsApp bot, website, POS, ERP)

```
[1] Customer checks out on merchant's WhatsApp bot / website
      → KODA issues a Payment Intent: amount, currency, operator options,
        merchant's mobile money number, intent_id, 15-min expiry

[2] Customer pays the NORMAL way they already know:
      USSD (*150#, #144#, *501#...) or their operator app
      → sends amount to merchant's number. Nothing new to learn.

[3] Telco fires confirmation SMS to MERCHANT's SIM
      → KODA Sentinel (Android app on merchant phone) captures it locally,
        parses it on-device, pushes a signed structured record to KODA Cloud
        (~2–4 seconds after SMS arrival)

[4] Customer receives their own confirmation
      → types/pastes the reference code into the WhatsApp bot or web widget
        (or uploads a screenshot — Vision Agent extracts the code, §6.4)

[5] KODA MatchMaker Agent cross-verifies:
        reference code ↔ merchant SMS ledger
        amount ↔ intent amount
        timestamp ↔ intent window
        sender number suffix ↔ customer's WhatsApp/checkout number
        code never-used-before (global replay index)

[6] Fraud Sentinel Agent scores the match (§8). Score < threshold → auto-confirm.

[7] KODA fires `payment.verified` webhook to merchant's system
      → order confirmed, ticket issued, course unlocked, driver dispatched.

[8] Customer sees "✅ Paiement confirmé" in WhatsApp/web — total elapsed:
      typically 30–60 seconds, of which KODA's share is < 10.
```

**The magic sentence for the pitch deck:** *"Your customer pays exactly the way they paid yesterday. The only thing that changes is that your system finally knows about it."*

## 4. THE SENTINEL APP — ENGINEERING SPECIFICATION

| Concern | Design decision |
|---|---|
| SMS access | `RECEIVE_SMS` BroadcastReceiver filtered to known telco sender IDs only (M-PESA, OrangeMoney, AirtelMoney, Africell, MTNMoMo, Wave...). Non-payment SMS never read, never transmitted — enforced at code level and stated in privacy policy. Google Play SMS-permission policy risk is real: primary distribution is **direct APK + managed Play private channel + preloaded on KODA-certified devices**; Play public listing pursued under the "core functionality" exemption with a declaration (transactional SMS processing is an accepted use case, but plan for rejection and don't depend on it). |
| Parsing | On-device regex/grammar template pack per operator + per country, versioned, OTA-updated from cloud (no app update needed when a telco reformats its SMS). Unparseable messages → flagged raw (metadata only) to ParserAgent for template regeneration (§6.1). |
| Integrity | Play Integrity API attestation at registration + rolling checks. Each device holds a hardware-backed keypair; every record pushed is signed. A record from an unattested or cloned device is quarantined. |
| Offline | Congolese reality: power cuts and dead zones. Sentinel queues locally (SQLCipher), syncs on reconnect, cloud back-fills the intent-matching window. An intent whose SMS arrives late is matched retroactively and the webhook fires late rather than never (`payment.verified.late`). |
| Battery/perf | Event-driven only (no polling). Foreground service exemption not required; WorkManager for sync. Target: < 1% daily battery on a €80 Android. |
| Multi-SIM | Dual-SIM aware; merchant maps each SIM slot to an operator + till identity. |
| Feature-phone merchants | No Android? Merchant sets carrier-level SMS auto-forward (where supported) or manually forwards the confirmation to KODA's WhatsApp ingestion number — VisionAgent + ParserAgent structure it. Slower (30–90 s) but functional. Honest tier label: "KODA Lite". |

## 5. OPERATOR TEMPLATE PACKS (LAUNCH MATRIX)

Templates below are **calibration targets, not gospel** — exact wording varies by country, language, and telco firmware and drifts over time. This is precisely why parsing is template-pack-driven and OTA-updatable, with ParserAgent regenerating templates from drift (§6.1). Extracted canonical fields are constant across all operators:

`{ref_code, amount, currency, counterparty_name, counterparty_msisdn_masked, timestamp, balance_after, operator, direction}`

| # | Operator | Markets (launch scope) | Typical merchant-side confirmation shape (illustrative) |
|---|---|---|---|
| 1 | **M-Pesa (Vodacom)** | DRC, TZ, KE-style grammar | `{REF} Confirmé. Vous avez reçu {AMT} FC de {NAME} {MASKED_MSISDN} le {DATE} à {TIME}. Nouveau solde: {BAL}` |
| 2 | **Orange Money** | DRC, CI, SN, CM | `Vous avez recu {AMT} de {NAME} ({MSISDN}). Ref: {REF}. Solde: {BAL}` |
| 3 | **Airtel Money** | DRC, KE, UG, TZ, NG | `Txn ID: {REF}. Recu {AMT} de {MSISDN} {NAME}. Solde {BAL}` |
| 4 | **Africell Money** | DRC, SL, GM | `{REF}: reception de {AMT} de la part de {NAME}` |
| 5 | **MTN MoMo** | GH, UG, CI, CM, RW | `Payment received: {AMT} from {NAME}. Ref {REF}. Current balance {BAL}` |
| 6 | **Wave** | SN, CI, ML, BF | `Vous avez reçu {AMT} de {NAME}. ID: {REF}` |

**Phase 1 GA:** the four DRC operators (M-Pesa, Orange, Airtel, Africell) — home-turf calibration with Tunakula and Scan & Go as live in-house proving grounds. **Phase 2:** MTN MoMo + Wave for CI/SN/GH expansion. Reference-code grammar (length, charset, prefix pattern) is validated per operator as an anti-fraud pre-filter before any ledger lookup.

## 6. THE AGENT MESH — KODA AI-OS (LangGraph, 9-agent registry)

This is where KODA stops being an SMS parser and becomes an **agentic verification OS**. Registry follows the NSEYA X-EXECUTE convention; every agent is a LangGraph node with typed state, event-sourced decisions, and a human-escalation edge.

| ID | Agent | Mission | Trigger | Autonomy |
|---|---|---|---|---|
| K-01 | **ParserAgent** | Structure raw SMS; detect telco format drift; auto-generate + canary-test new parse templates and push OTA to Sentinels | Unparseable/low-confidence SMS | Auto-deploy after canary pass on 50 msgs; human sign-off if field-mapping changes |
| K-02 | **MatchMaker** | Core verification: code↔ledger↔intent↔amount↔window↔msisdn-suffix matching, incl. fuzzy repair of customer typos (O/0, I/1, transpositions) with edit-distance ≤ 2 against candidate set | Customer submits code | Full auto within fraud threshold |
| K-03 | **FraudSentinel** | Real-time risk scoring of every match (§8); maintains Global Replay Index; velocity, device, and behavioural signals | Every match attempt | Auto-block high score; queue mid-band for review |
| K-04 | **VisionAgent** | Extract ref/amount/time from customer screenshot uploads; run forgery forensics (ELA, font-metric consistency, status-bar coherence, known-editor artefacts). Screenshots are **assistive evidence only — never sufficient alone**; final truth is always the merchant-side ledger | Image upload in WhatsApp/web | Extraction auto; forensics feed FraudSentinel |
| K-05 | **ReconcilerAgent** | Nightly + on-demand three-way reconciliation: merchant SMS ledger ↔ verified intents ↔ merchant's declared orders; surfaces unmatched receipts ("you were paid 3× with no order — recover them"), duplicates, gaps | Cron + dashboard | Report auto; corrections proposed, merchant-approved |
| K-06 | **DisputeAgent** | Guided resolution when match fails: interviews customer in-channel, requests screenshot, checks late-SMS back-fill, produces an evidence file, recommends outcome | Failed/contested verification | Recommends; merchant decides (v1). Auto-resolve for clear-cut classes in v2 |
| K-07 | **LinguaAgent** | All customer-facing verification dialogue in FR / EN / Lingala / Swahili / Wolof / Twi, tone-matched to WhatsApp commerce norms | Every customer interaction | Full auto |
| K-08 | **OpsPilot** | Fleet health: Sentinel heartbeat monitoring, offline-merchant alerts, parse-success-rate per operator, webhook delivery health, anomaly paging | Continuous | Auto-alert; auto-remediate known classes (resync, template rollback) |
| K-09 | **COSA-K** (Chief of Staff) | Cross-agent orchestration, policy enforcement, escalation routing, weekly merchant intelligence brief ("your peak payment failure window is Friday 18–20h — here's why") | Orchestrator | Supervisory |

**Agent design law (portfolio-wide):** every autonomous confirmation is replayable — the full decision trace (inputs, scores, template version, model version) is written to the CQRS event store. A verification you cannot audit is a verification you cannot defend in a dispute.

## 7. THE API — DELIBERATELY TINY

Three core endpoints. If a developer can call Stripe, they can call KODA in one coffee.

**Base:** `https://api.koda.africa/v1` · Auth: `Authorization: Bearer sk_live_...` · All webhooks HMAC-SHA256 signed (`X-Koda-Signature`), 5 retries with exponential backoff, replay-protected with timestamp tolerance ±300 s.

### 7.1 Create Payment Intent

```http
POST /intents
{
  "amount": 25000,
  "currency": "CDF",
  "operators": ["mpesa_cd", "orange_cd", "airtel_cd"],
  "customer_msisdn": "+24399XXXXXXX",     // optional, sharpens matching
  "metadata": { "order_id": "TNK-88213" },
  "expires_in": 900
}
→ 201
{
  "intent_id": "int_9f3KODA71",
  "status": "awaiting_payment",
  "pay_to": [
    { "operator": "mpesa_cd",  "number": "+243812345678", "ussd_hint": "*1122#" },
    { "operator": "orange_cd", "number": "+243892345678", "ussd_hint": "#144#" }
  ],
  "expires_at": "2026-07-17T14:47:00Z"
}
```

### 7.2 Submit Verification Code

```http
POST /intents/{intent_id}/verify
{ "reference": "CI240717.1432.A88213" }        // or: { "screenshot": "<base64>" }
→ 200
{
  "status": "verified",                        // verified | pending_review | rejected | not_found_yet
  "verified_at": "2026-07-17T14:33:09Z",
  "operator": "orange_cd",
  "amount_confirmed": 25000,
  "match_confidence": 0.998,
  "receipt_id": "rcp_KODA_7f21"
}
```

`not_found_yet` (SMS lag / Sentinel offline) → KODA keeps watching the ledger for the intent window and converts to webhook-on-arrival. The customer is told, in their language: *"Ton paiement est en route — on te confirme dès que le réseau nous le montre."*

### 7.3 Webhooks

```json
POST {merchant_webhook_url}
{
  "event": "payment.verified",
  "intent_id": "int_9f3KODA71",
  "receipt_id": "rcp_KODA_7f21",
  "amount": 25000, "currency": "CDF",
  "operator": "orange_cd",
  "reference": "CI240717.1432.A88213",
  "payer_name_masked": "J*** N.",
  "matched_msisdn_suffix": "***4521",
  "risk_score": 0.02,
  "verified_at": "2026-07-17T14:33:09Z",
  "metadata": { "order_id": "TNK-88213" }
}
```

Event catalogue: `payment.verified` · `payment.verified.late` · `payment.rejected` · `payment.pending_review` · `intent.expired` · `dispute.opened` · `dispute.resolved` · `sentinel.offline` · `reconciliation.report`.

Also in v1 (secondary surface): `GET /intents/{id}`, `GET /receipts`, `GET /reconciliation/latest`, `POST /disputes/{id}/resolve`.

## 8. FRAUD ENGINE — THE PART THAT DECIDES IF THIS PRODUCT LIVES

The screenshot-fraud economy exists because merchants verify against **customer-side** artifacts. KODA's structural advantage: the source of truth is **merchant-side**, telco-issued, device-attested. A fraudster would need to forge an SMS *into the merchant's own phone*. Residual attack surface, and the answer to each:

| # | Attack | Countermeasure |
|---|---|---|
| 1 | **Code replay** (reuse a real old payment's code) | Global Replay Index — every code is single-use per merchant, forever. Second submission → instant reject + fraud flag on submitter identity. |
| 2 | **Code theft** (fraudster grabs a code the real payer posted publicly) | Multi-factor match: msisdn-suffix ↔ checkout identity, amount exactness, ±window tightness. Suffix mismatch → `pending_review`, DisputeAgent challenges ("confirm the last 3 digits of the number you paid from"). |
| 3 | **Forged screenshot** | Screenshots are never sufficient — extraction convenience only. Truth = merchant ledger. VisionAgent forensics additionally burn known editing toolchains into FraudSentinel features. |
| 4 | **Spoofed SMS to merchant phone** (fake sender-ID SMS) | Sender-ID allowlist + grammar validation + **balance-continuity check**: each genuine telco SMS carries `balance_after`; a spoofed message breaks the running balance chain. Chain-break → quarantine + merchant alert. This is the deep defence competitors won't think of. |
| 5 | **Malicious/compromised Sentinel device** | Play Integrity attestation, signed records, per-device anomaly baselining (K-08), instant device revocation. |
| 6 | **Merchant self-fraud** (fake receipts to game a marketplace) | Balance-chain + cross-merchant code collision detection + platform-level trust scoring exposed to marketplace operators via API. |
| 7 | **Payment-then-reversal** (payer initiates telco reversal after goods released) | Reversal SMS is also parsed → fires `payment.reversed` (v1.1) so the merchant system can react. Documented honestly: KODA cannot *prevent* telco-side reversal; it can make the merchant the first to know. |

Risk score = gradient-boosted model over ~40 features (match geometry, velocity, device, historical payer graph, balance-chain health), retrained per corridor. Bands: `<0.15` auto-confirm · `0.15–0.6` DisputeAgent challenge · `>0.6` reject.

## 10. HONEST LIMITATIONS (in the docs, on purpose — this builds more trust than hiding them)

1. **Latency floor is the telco's, not ours.** If the confirmation SMS takes 4 minutes during network congestion, verification takes 4 minutes. KODA's own processing is < 10 s; the SLA language must separate the two.
2. **No payment initiation in v1.** The customer still dials USSD themselves. (Roadmap: assisted-USSD deep links now; STK-push via aggregator partnership later, as an *optional* premium rail — never a dependency.)
3. **Funds still sit on the merchant SIM.** KODA verifies; it does not settle, sweep, or hold. Treasury/sweep is BitriPay's job downstream, cleanly separated for licensing reasons.
4. **Google Play SMS policy is a live risk** — mitigated by distribution strategy (§4), never assumed away.
5. **A determined merchant-side insider with the merchant's own phone can create real ledger entries** — because they'd be real payments. KODA verifies payments, not business ethics.
6. **Telco format drift will break parsing periodically.** That's why drift-detection + OTA template packs is a core competence, not an edge case.

## 11. COMPLIANCE POSTURE

- **Licensing:** KODA performs no fund transmission, holds no float, executes no payment orders → positioned outside EME/établissement de paiement scope in DRC (BCC) and analogous regimes. Formal legal opinion per market before GA is a launch gate, not an afterthought. Where BitriPay's EME licence lands, KODA slots under it as the verification layer.
- **Data protection:** SMS payment data is personal + financial data. Per-merchant data residency options (GCP `europe-west` default; in-country/S3-compatible mirror where mandated). Payment-SMS-only capture enforced in code; DPIA published; masked msisdn everywhere except fraud pipeline; customer-facing consent language written by humans, in French first.
- **Auditability:** CQRS append-only event store = every verification is replayable with full decision provenance — the dispute-resolution and regulator-conversation superpower.
